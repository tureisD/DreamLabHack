# Repair the task before buying a fine-tune

The Guide now asks operators to test a cheap change when labelled baseline runs fail. **Repair first** checks camera freshness, arm readiness and station faults, then offers a predeclared comparison of the original task with one changed prompt or one physical setup change. Both arms of a pair use the **same checkpoint and matched diagnostic scene**. The plan balances run order, saves every attempt, and requires reviewed outcomes and a scene-reset attestation before a decision. Robot motion still needs a supervised Start action for each run.

The candidate prompt is sent only for that diagnostic trial; the task's stored instruction is not changed. A setup change is an operator instruction and cannot be enforced by software. In both cases, keep the success rule fixed. This path does not change model weights or action horizon.

The saved audit binds each reviewed attempt to its source rollout metadata and checks unique sessions, timestamps after the frozen plan, prompt, checkpoint, completion and safety-stop counts. A two-sided conservative paired-difference bound must clear the predeclared minimum gain before the UI recommends keeping the cheap fix. When the full comparison observes no gain, it recommends reviewing targeted demonstrations and FaaS; that is not proof a different prompt or setup could never help. Incomplete, changed, or unreviewed evidence is not silently dropped.

This flow may prevent an unnecessary paid job for a task that responds to a prompt or setup repair. **It does not measure money saved by itself**, because the unrun FaaS counterfactual is unknown. The separate [operator study](benchmark/README.md) compares real workflows on a frozen horizon, logging validation, time, demos, jobs, steps and actual bills. Its bundled numbers are synthetic. A verified improvement in the apple checkpoint demonstrates task performance in simulation, not a reduction in operator effort caused by this coach.
